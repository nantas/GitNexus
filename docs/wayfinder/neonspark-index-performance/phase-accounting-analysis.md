## 生命周期和候选门槛

- glob 边界 heapUsed 约 83→519 MB，但首次 snapshot 后已下降，pipeline 开始时约 110 MB。不能声称这批临时对象一直存活到 FTS。glob 在此轮只有 3.042 秒，不值得为它引入一套跨阶段扫描缓存或改变可选 grammar 的警告/加载行为。
- pipeline 返回 heapUsed 约 1.57 GB，CSV 完成约 0.96 GB，最终身份复核开始约 0.61 GB。边界值不是峰值；不能用它们推断 native 内存已经释放。
- parse→scope 已复用 ParsedFile。C# 此轮 9,281 个 scope 文件有 9,184 个 pre-extracted hits；余项仍承担 fallback/完整性职责。再次添加同类解析缓存不能消除整段 95 秒。
- snapshot→parse 的全内容缓存会延长原始内容生命周期，还不能替代最终独立核验；仅 C# 原始内容约 125 MB，无法解释资源/CSV 的 GB 级工作量。暂不以大缓存实现。
- graph 在导入后仍被 embeddings、结构关系完整性及调用摘要读取，返回契约也暴露 pipelineResult。直接 clear 或提前 native close 不满足语义与安全约束；此前强制 GC 与 2/4 GiB FTS 池失败证据仍成立。
- 资源 discovery→binding 重读约 5 GB，值得先测有界投影的规模：只保留现有轻量解析器实际消费的对象头与 MonoBehaviour 行，同时保存原始行号。筛选脚本只计数，不写出大缓存；规模通过后仍须完整绑定等价性、变更拒绝、取消和 spill/清理证明。

原始探针和账本位于 `.scratch/neonspark-accounting-20261026/`。候选筛选和全量校验结果完成后补入决议；此文不提前宣告采纳任何新产品优化。

## 有界投影筛选与等价原型

3,059 个选中大资源共 4,812,344,180 字节、165,369,831 行。保留原轻量解析器可观察的对象头和 MonoBehaviour 行，并带原始行号，得到 3,394,224 行、约 164 MB 的投影（原始字节的 3.4%）。不改变小资源的完整 YAML 解析路径。

独立原型将记录按原路径顺序写入既有 ResourceRecordStore：记录预算 1 MiB，按约 64 KiB 估算块批量追加；块可能超出阈值一个受 256 KiB 行上限约束的条目。预算不等于整个 JS 堆上限，还存在当前行、序列化和解析临时对象。实际 spool 写入/读回各 165,161,877 字节，记录预算观测峰值 1,035,498 字节，完成后已删除 spool。

全部 60,023 个绑定（含组件 ID、行号、证据和完整引用）原实现/投影回放摘要一致：`432b70b0a2844c8a52ffadd3bf98d58d3a73b5fa0d616affa1fd163c237464ed`。原读取绑定 20.729 秒，投影回放 1.140 秒，独立投影生成 20.062 秒。**生成成本不能遗漏**：候选要把生成并入原本必需的 discovery 流，才可能有净收益；这组回放不是完整构建提速证明。

隔离候选已接入 discovery→session，仍执行 discovery 前后、binding 前后文件状态检查；中间变更拒绝复用。结束时排空并验证未消费记录的 checksum，取消/错误清理只删除 owned spool。自检覆盖 CRLF、Unicode、巨大 scalar、引用 spill、取消、文件变更、合法 JSON 损坏和清理。51 项原生资源/发布回归通过；原“读两次”的性能断言在候选副本中更新为大资源一次读取，其组件、summary、parity 断言保留。第一次副本测试因缺少源 fixture 和旧 opens 断言失败，日志保留，未把它算作成功。

## 内存预算筛选

在本轮完整索引的独立副本上，6 GiB 池完成全部 22 张 FTS 表重建，catalog、File 行数/内容长度及查询检查通过，FTS 61.976 秒。另对既有英文、中文、文件后段查询的完整返回 ID 集合进行了核对，通过。它没有 pipeline/COPY 工作集，因此不能直接替换完整构建默认预算，也不能和完整构建 FTS 的 74.315 秒比较收益。

当前完整验证限定为资源投影与 6 GiB 两个单变量候选。按 control→6 GiB→6 GiB→control→projection→projection→control 串行，每轮空索引/解析缓存，保留原 scope/defines/输入核验/full FTS。全量关系、内容、receipt、parity 与召回通过后立即回收 DB/缓存；严重退化的候选提前否决，不能把取消的重复写成已完成。产品源码暂未改变。

### 6 GiB 的完整构建否决

首个无探针对照 `control-a1` 成功，wall 452.759 秒、CPU 946.45 秒，全部内容、841,653 条关系、receipt、parity 和 FTS 召回通过。随后 `pool6-b1` 在 File FTS 开始后出现 `Invalid transaction type to rollback.`，FTS 表未 ready，最终以 **SIGSEGV** 退出（386.269 秒失败样本）。不能将该失败样本较低的 wall/峰值算作收益，也不能仅凭回滚错误推断底层一定是 buffer exhaustion。

**不采纳 6 GiB 配置**，取消 `pool6-b2`，保留原预算。独立 reopen/rebuild 通过而全量 COPY→FTS 失败，证明两种验证上下文不可互相替代；不为采用降预算而去修补 native 引擎或降低 FTS 完整性。原索引 stat/哈希核对未变，`/cores` 为空；失败索引约 4.75 GB 已回收。实验继续运行资源投影的两对完整对照。
