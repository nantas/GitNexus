## 第二轮进展

- 用户回复“Q1 同意；Q2 我需要知道现有可能的方案需要多少缓存空间”：对应上一轮问题，确认日常小改 60 秒内完整可查询作为设计目标；缓存预算尚未决定，先提供容量依据。该目标不是已验证的承诺。
- 只读容量核对：现有正式索引约 5.6 GiB，现有 parse-cache 占用约 298 MiB；最新实验 metadata 的 155,816 项 fileHashes JSON 为 23,058,079 字节，完整输入 receipt 为 164,034 文件。
- 已保存实验产物：选中 Unity/流程事实未压缩 360,926,871 字节，gzip 24,492,445 字节；parity seed 未压缩 7,824,499 字节。它们是已解析结果/验证产物，缺少部分失效依据，不能直接当可复用原始事实缓存。
- 历史大资源投影原型约 158–166 MiB，仅覆盖大资源行投影，不代表完整缓存，也不表示旧原型重新获准采纳。此前统计 File 全文约 9.79 亿字符；全文缓存不是几十 MiB 量级。
- 一份完成后的最新实验索引及缓存共 6,964,417,290 字节（约 6.49 GiB）；这个数字不等于构建期间峰值。新增缓存预算不能替代旧新索引共存、CSV/WAL 等临时空间预算。
- 规划估算（未实现/未实测）：完整输入历史约 30–80 MiB；紧凑资源事实、GUID/候选与依赖凭据约 0.3–1 GiB；额外正文缓存约 1 GiB 起，连大资源原文也保留则可能达 5–8 GiB。不同表示可能重叠，不能简单相加，精确容量须等记录结构确定后验证。

## 新发现的正确性约束

现有 discovery 会过滤未知 script GUID、未解析的 prefab 目标；资源命中数又参与同名脚本 canonical 选择。因此不能直接按资源文件 hash 复用现有 discovery 输出，也不能认为 resource-only 变化只影响该资源。需要保留足以失效的原始引用、候选和依赖事实，或在无法证明局部影响时回退全量。上述规划容量已包含为这些凭据留余量的意图，但不是已测容量。

## 第四轮已确认

- Q5：首个加速场景为现有 C# 方法体修改，不改变声明或 Unity 资源；资源修改另行讨论。方法体变化仍可能改变调用和流程事实，不能视为纯局部输出替换。
- Q6：不引入额外常驻进程监控；每次独立 CLI 的输入核验成本计入端到端目标。用户要求先解释完整输入核验的业务流程与耗时，再讨论方案。
- 当前 watch 是内存触发队列，没有跨 CLI 的持久事件凭据；实际分析仍执行两次完整 Unity 快照。拒绝常驻监控不等于放弃现有可用的可靠快速核验机制，因为该机制目前尚未建立。
- 当前快照分为候选/源文件/项目输入枚举、scope/ignore 筛选、meta/控制文件补齐、逐文件 stat→完整内容 SHA-256→stat、输入路径与配置摘要聚合。开始快照用于比较上次发布凭据，结束快照用于拒绝构建期间输入漂移；无变化复用只做开始快照。
- 最新已采纳候选两轮开始/发布核验分别为 118.445/47.421 秒、37.717/67.027 秒。两轮总核验 165.866/104.744 秒，不能用解析缓存或局部图更新直接消掉。
- 历史细分样本（164,024 文件、每次约 6.20 GB，非当前 164,034 文件基线）显示，首次/发布核验 31.798/45.403 秒；文件 stat/读取/哈希占 17.649/29.270 秒，source 枚举及 ignore 等占 9.315/10.414 秒。另一次操作诊断 SHA 计算约 2.4 秒，不能把整个读取哈希阶段归因于摘要算法。
- 完整核验是现有保守保障，不是文件系统原子快照：两次摘要相等加单文件读前后属性检查仍不证明整个分析期间从未发生改动后恢复。未来方案需明确一致性边界，不夸大现有保证。
