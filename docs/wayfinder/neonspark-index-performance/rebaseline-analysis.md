## 新方向与本轮验证

### 1. 优先补齐编排层耗时和数据生命周期

把 CLI 引导、可选语法预检、runner 身份计算、配置/写入目标解析、Git 元数据扫描、发布 metadata 计算、最终身份复核分开计时。它们分布在 pipeline 之前/之后，旧优先级未完整覆盖。

已由源码确认两个入口：

- `cli/analyze.ts` 为可选语法警告单独执行仓库 glob，再进入 `runFullAnalysis`。预检使用自己的排除规则，不能直接假设与正式 scope 枚举等价。
- `run-analyze.ts` 在发布 metadata 中调用 `listWorkingTreeDirtyPaths`，它执行完整 untracked porcelain 和 hidden-index 标志枚举；之后还有 `finalizeAnalyzerRunnerIdentity`，然后才开始最终 snapshot。Git 的失败保守行为、rename 两端、assume-unchanged/skip-worktree 语义都不能削弱。

原图严重过期，两个新符号 context 未找到，已按源码核实上述位置；没有把空图结果当作低风险，也没有修改函数。

**本轮做了低成本只读反向顺序探针**，直接调用原 glob/原 dirty-paths 实现，无 DB、无新索引：

| 操作 | 第一轮秒 | 第二轮秒 | 结果一致性 |
|---|---:|---:|---|
| optional grammar glob | 2.026 | 2.074 | 两次均 0 个命中，列表 SHA 相同。 |
| Git dirty paths | 1.624 | 1.811 | 两次均 18 路径，列表 SHA 相同。 |

结构化证据见 [preflight-probe.json](preflight-probe.json)。当前未复现 77/92 秒，因此**不能认定 glob 或 Git 是根因，更不能宣称消除这两个调用就能省相应时间**。下一项是在真实构建中以少量边界计时闭合整轮账本，并同时观察对象何时可释放；先判断是重复工作、身份校验、Git 扫描还是环境等待，再挑实现。

### 2. 用全生命周期成本选择复用边界

不预设“加缓存”或“提高线程数”。建立每阶段输入字节/派生表示、生成时刻、最后使用时刻及重复解析次数的清单，寻找可保留等价证据、且不延长大对象生命周期的复用点。候选范围应包括输入快照→parse、parse→scope、资源 discovery→binding、graph→CSV/FTS，而不只沿用资源或 CSV 方向。

已知资源两阶段约 5.705/5.301 GB 的读取和大 prefab 86.8% 字节占比提供规模线索，但不是复用正确性的证明。新方案必须有有界预算，保持两次独立输入核验、逐组件/行号证据、canonical 顺序、错误和取消语义；禁止为了试验再次保留多份 GB 级全量内容缓存。

按预计可消除的**总工作量**、峰值和完整 wall 给候选排序，而非单个函数变快。跨阶段复用只有在成本总账支持后才做最小原型；旧候选结论只作为已知边界，不限定新方案。
