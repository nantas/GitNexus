# 降低 full-content FTS 构建成本


已于 2026-10-26 按现有候选决策收口：线程池 16 未通过无探针整轮 wall/CPU 门槛，不采纳；实际中英及后段 FTS 召回和错误回归通过。 完整证据见[现有验证项收口与候选否决](resolution.md#现有验证项收口与候选否决2026-10-26)。下文为历史调查顺序；关闭本票不表示 180 秒目标已达成。

## Question

完整内容导入及 File.file_fts 的波动，分别有多少来自源文件读取、CSV 转义/写盘、native CPU 与内存压力；是否存在保持完整搜索语义的安全优化？

## Evidence and next experiment

- **当前结论**：[线程池完整构建交替验证](resolution.md#线程池完整构建交替验证2026-10-26)已完成四次完整构建，默认 514.982/550.903 秒、16 线程 364.263/349.393 秒；内容/关键图事实均一致，反向对全部 841,653 条关系一致。候选保留、未修改默认值。下一步由[作用域准备调查](scope-resolution.md)拆分更大的配置/扫描等待；随后关闭探针做完整交替验证并补 FTS 召回。以下为历史调查顺序。

- **最新原生追踪**：[小文件原生操作与线程池对照](resolution.md#小文件原生操作与线程池对照2026-10-26)。复用原 FileContentCache，固定 128,034 个 `.meta` 的逐文件 SHA；已区分 stat/open/fstat/read/close。前置读取 4.97 GB 大资源后出现 41.179 秒慢回放，read/fstat/close 等待升高，但重复默认组仅 6.863 秒，大资源读取并非充分复现条件。
- 诊断进程线程池 16 的两次回放为 6.198/6.143 秒，close 等待下降；反向默认组 6.863 秒，快区间仅省约 0.720 秒、CPU 增约 40%。**线程池排队保留为下一候选，不改默认值。** 下一步在真实 CSV 慢阶段使用已验证的原生追踪，再做完整构建默认/16 单变量对照，检查 CPU、峰值、其他阶段与完整输入/图/FTS 语义。原生事件跨度含排队、服务及回调调度，不能等同于纯磁盘时间。

- **最新定位**：[CSV 预读长尾定位](resolution.md#csv-预读长尾定位2026-10-26)。相同探针捕获 CSV 17.548/180.629 秒，慢样本自身 95.1% 时间在预读等待；转义、规范化、输出 write/drain 与关系阶段没有对应长尾。128,034 次 `.meta` readFile 平均约 0.606/15.015 ms，优先拆解小文件访问。慢样本最终因输入变化被拒绝发布，不能作成功全量 A/B 或宣称完整事实等价；原索引保留。
- 下一步先固定回放输入及逐文件 SHA，再追踪原 readFile 路径中的 open/fstat/read/close 和排队时间，关联设备 I/O/事件循环。若源盘等待主导，再用相同字节的独立内置副本交替回放；明确设备/文件系统/缓存一起变化的限制，不直接改预读并发、线程池或跨阶段缓存。整机 swap 只能作背景证据。
- 当前快路径不支持优先重写转义/行缓存，也不支持提前释放 native DB。两对 File-only 回放输出 155,808 行、1,011,907,990 字节 CSV，SHA 一致，耗时 7.580–12.599 秒，未复现长尾；回放不是完整 pipeline/FTS 验收。

- **下一主项**：[持续补位完整构建与压力归因](resolution.md#持续补位完整构建与压力归因2026-10-26)。当前 164,026 文件输入的 A/B 中，CSV emit 122.308/27.525 秒，File FTS 45.139/72.086 秒；最终哈希 CPU 仍约 143 秒。整机换页活跃且两组压力不同，不能把总体差异归因于哈希调度。本票恢复为下一主调查项。
- 先对既有 CSV 路径做轻量分段：源内容读取 wall/CPU/字节、转义序列化 CPU、输出 write/drain 等待与待写字节；按内容类型/大小聚合，保持读取与预读策略不变。同步记录 GC、进程页故障及整机 swap 增量，区分进程证据与系统背景；不使用整机计数直接归因。
- 先用同一实现捕获快慢样本。只有读等待占主导时才做同内容在外置源盘/内置临时副本的交替回放；若转义分配或 drain 占主导，再分别验证分配削减或输出背压。回放用于归因，不能替代完整构建验收。不要同时改存储位置、并发、buffer pool 或 native 生命周期。

- 当前：[三对验证已完成](resolution.md#无采样器三对验证与存储等待转向2026-10-26)，未采纳小缓冲作为耗时优化。下一主项仍由输入核验票承接，改测操作级文件访问等待；native 生命周期调查保留，不能解释无 DB 时的慢枚举。

- 最新：[GC 归因与小文件缓冲候选](resolution.md#gc-归因与小文件缓冲候选2026-10-26)。已得到 GC/Buffer 分配对照，下一主项转到[输入核验](input-validation.md)的无采样器重复 A/B；B 峰值较高，暂未采纳。FTS/native 生命周期调查保留在其后。

- 2026-10-26 已完成[完整构建核验分段](resolution.md#完整构建内的核验分段2026-10-26)：相同读取量下，最终哈希段 wall 17.649→29.270 秒、进程 CPU 34.685→121.884 秒；尚未复现 165 秒慢样本。下一步先测 snapshot 临时分配/GC，再决定是否调整 native 生命周期。

- 2026-10-23 进展见[FTS 与核验压力续查](resolution.md#fts-与核验压力续查2026-10-23)。2/4 GiB 池在 File FTS 上耗尽，8 GiB 通过；不下调默认预算。FTS 前 GC 可回收 1.420 GiB，但完整构建 457.981 秒、发布前核验 165.398 秒，稳定收益未证实。
- 历史计划中的完整构建 snapshot 分段已完成，下一实验以上述 2026-10-26 结论为准；pipeline→DB 临时堆定位保留。当前仍 open，未采纳产品改动。

- P0 新基线与分段证据见[重复测量条件决议](resolution.md#重复测量条件决议2026-10-23-续查)。本票为下一主研究项；不得再用历史旧输入的 436 秒做直接 A/B。
- 优先围绕 File.file_fts 前/中/后及发布前核验记录进程 CPU、JS heap、native footprint、整机换页。只在安全生命周期边界做单变量试验；先核实对象何时可释放，不假定 retained heap 或 native buffer 就是根因。

- 按表记录 FTS wall、输入内容字节、buffer pool、数据库体积和 page-in，区分 CPU 工作与 I/O 等待。
- 检查 Apple Silicon 页粒度相关预算与实际用量，不能盲目降低 COPY 安全下限或扩大默认内存。
- 只在测量支持时试验批次/执行顺序/安全资源生命周期；不得触碰已知 native destructor/worker shutdown 安全约束。
- 保持 full content、既有表覆盖、CJK/换行分词、失败恢复及 embeddings 保留行为。
