# 拆分纯代码与 Unity 资源分析基线

## Question

纯代码完整索引的成本是多少？资源需求额外引入哪些输入、算法与持久化成本，哪些范围可以从需求出发简化？

## 授权与口径

2026-10-27 用户要求暂停围绕核验耗时收敛，先分别测量不含/包含 Unity 资源的分析，再深入资源流程与算法。这授权隔离诊断实验，不代表采纳范围缩减或放宽一致性。

- 纯代码：原 Assets/、Packages/ 中 C# 源码；保留原 defines、C# 项目/namespace 依赖、解析、调用/继承、MRO、社区、普通流程及代码派生 Unity lifecycle/process；保留代码全文与 FTS。排除资源分析和 `.meta` 的图/全文工作。
- 完整：当前已采纳实现，原 `.cs,.meta` 普通扫描，加现有 Unity 资源读取与派生能力。
- 没有现成的完整资源关闭开关。仅 `.cs` extensions、空资源 scope 或禁用 prefab source emission 均不足。仅在 scratch dist 副本将资源 phase 置为空操作，并使两次输入 receipt 只覆盖代码和有关配置依赖；源码和正式 dist 不变。
- 顺序：纯代码 → 完整 → 纯代码；串行、空索引/解析缓存、Node 24.15.0，不清 OS 缓存。分组输入凭据、阶段 wall、CPU、峰值、文件/关系及 FTS 分别记录。两组功能不同，不作等价优化宣称；完整减纯代码也不等于单个资源函数净耗时。
- 相同轻量输入哈希证据落盘与 I/O 观察器用于两组；纯代码读取资源/meta 会失败并记录。观察计数是 API 调用数，非唯一文件数或物理磁盘读取次数。
- 检查隔离 snapshot 对代码变化敏感、对排除资源变化不敏感；检查代码组两轮输出/输入一致、FTS 实际召回，完整组与历史输入相同才做跨轮比较。失败和漂移样本保留。
- 每轮导出必要证据后删除该轮独立 DB/解析缓存；不改原 neonspark 索引/业务文件/全局 CLI，不新增常驻进程。

## 证据

资产位于 `.scratch/neonspark-code-resource-20261027/`。运行前图查询 partial，两个修改点 impact UNKNOWN/未找到；已核对当前 run-analyze 两次 snapshot 调用、pipeline 注册与单元测试，隔离修改仅影响诊断副本。

实验设置记录：首次启动因诊断副本缺少 vendor/leiden，在分析前失败（4.737 秒），保留为 `code-a1-setup-failed`，补齐 package 资产引用后重跑，不计有效样本。第一轮 I/O 观察器仅覆盖用户路径别名，后续补充实际 realpath，故第一轮的零资源读取计数不能独立证明没有读取；第二轮纯代码使用完整路径检查，并以相同输入/输出复核。这个观察器差异也意味着两轮纯代码 wall 仅作为基线范围，不是严格单变量收益实验。

## Resolution

已完成三轮隔离测量，结果落盘于 [code-resource-baseline-results.json](code-resource-baseline-results.json)。原完整基线 `baseline-current.json` 不被能力裁剪后的基线替换。纯代码参考为最后一轮 code-a2，两轮均保留；不是稳定 SLA。

| 指标 | 纯代码 A1 | 完整 B1 | 纯代码 A2 |
|---|---:|---:|---:|
| 完整 wall 秒 | 532.036 | 879.226 | 154.657 |
| 进程 CPU 秒 | 489.32 | 799.52 | 409.85 |
| 峰值 footprint GiB | 5.141 | 11.981 | 4.898 |
| 输入文件数 | 16,384 | 164,034 | 16,384 |
| 最终 File 行数 | 9,281 | 155,816 | 9,281 |
| 全部关系数 | 362,723 | 841,787 | 362,723 |
| 普通扫描秒 | 16.304 | 23.531 | 12.093 |
| 解析秒 | 64.374 | 47.503 | 39.420 |
| 作用域解析秒 | 122.874 | 37.040 | 35.696 |
| Unity 资源 phase 秒 | 0 | 76.576 | 0 |
| CSV/初始化/COPY 日志区间秒 | 23.943 | 31.002 | 9.942 |

两轮纯代码输入、File 内容及全部关系哈希一致，22 个 FTS ready，中英文与 >10 KiB 后段关键词实际召回通过。A2 的完整路径 I/O 观察器仅观察到 `.cs`、`.csproj`、控制文件与 JSON，不出现资源/meta 读取；这是受观察 Node 文件接口的证据，不是对 Git 子进程等所有系统调用的追踪。

完整 B1 的输入 receipt、155,816 个 File 内容和全部 841,787 条关系与先前 lazy-b2 完整基线一致。两组共同的 9,281 个代码 File 内容、所选代码符号表的 109,638 条 id/path/name/行号记录一致；不将它扩大为“全部派生行为完全相同”。完整 metadata 的 stats.files 为普通扫描的 137,321，表中采用实际数据库最终 File 行数，包含资源补建节点。

完整组资源成本：discovery 19,541 次打开、5,731,886,281 字节、36.094 秒；resolution 16,619 次打开、5,309,326,100 字节；canonical 8.4 ms，失败 0。两种读取合计约 11.04 GB 是逻辑读取量，不是物理磁盘流量，且未包含核验/CSV。发现记录约 30.59 MB 写入并回读临时存储，不能从重复读取字节直接推出投影缓存收益。

两轮纯代码 wall 范围 154.657–532.036 秒，中位数 343.347 秒；两轮不足以建立稳定分布。完整 B1 的开始核验为慢样本，不能用 879.226 减 154.657 秒宣称资源算法净成本为 724.569 秒。保留分阶段账本及启动/发布残差；日志区间不是独立函数计时。两轮纯代码观测器覆盖差异见设置记录。

三轮验证后共回收 10,541,092,206 字节（约 9.82 GiB）独立索引/缓存。原 neonspark metadata/seed 内容哈希与 DB inode/size/mtime 均保持不变。保留设置失败和有效样本，不留实验数据库。

## 下一方向

详见[资源需求与范围分析](resource-requirements-analysis.md)。优先分开“代码解析目标”“解析所需外部证据”“资源结构候选”“File/全文索引对象”，验证目录剪枝与 `.meta` 物化范围；再按真实需求研究 Serializable 提取和小资源对象解析。不实施新缓存框架或以减少能力冒充原目标达标。

本轮验证：隔离快照自检、三轮完整构建、跨轮输入/内容/关系比较、实际 FTS 检索、代码符号记录比较、原索引保护与文档 whitespace。正式源码/dist 与当前基线 pin 一致；未运行全仓 npm test/tsc，因为没有新增产品代码变更。
